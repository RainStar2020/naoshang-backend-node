| ---------------- | --- | ------- | ------ | ------- | ------ | ----- | --- | ----- |
| 普通用户             | 0   | —       | —      | —       | —      | —     | —   | —     |
| **VIP**（1阶·小批发商） | 1   | 9,980   | 7,980  | 7,980   | 2,000  | 20.0% | 5%  | 8 折   |

| **联创**（4阶·总批发商）  | 24  | 239,800 | 6,500  | 156,000 | 83,800 | 34.9% | 15% | 6.5 折 |

**关键点**

- 每档的「拿货单价」既是**自己的进货成本**，也是**自己卖给下级的名额单价**。
- 总部拿货价 6,500 = 联创拿货价，所以联创从总部进货不赚差价（这也是联创之间平级的根源）。
- 名额换算是全局统一的：**1 联创 = 4 私董 = 8 天使 = 24 VIP**。
- **「产品折扣」= 本档拿货价 ÷ 产品零售价**（VIP 7980/9980 ≈ 8 折、天使 7500/9980 ≈ 7.5 折、私董 6980/9980 ≈ 7 折、联创 6500/9980 ≈ 6.5 折），**仅适用于产品购买**。
  > 🔄 2026-10-26 更名：原「复购折扣」→「**产品折扣**」——因为"复购"在系统里语义更宽（推荐开店老板等业务也归入复购类流水），但推荐开店**并不打折**；只有**买产品**才享受本档拿货价折扣。更名以消除歧义，数值与代码逻辑不变（折扣即拿货价，无独立折扣常量）。

## 二、名额流转规则（核心）

### 2.1 谁能卖给谁

```
总部 ──(仅联创可买)──→ 联创 ──→ 私董 ──→ 天使 ──→ VIP ──→ 普通用户
```

- **只有联创能直接向总部买名额**。
- 其他所有档位（私董/天使/VIP/普通用户）**只能向自己绑定的直接上级购买**，不能跨级、不能跳过上级找总部。
- 因此每笔交易都会形成一条**采购链**：`买家 → 上级 → 上级的上级 → … → 联创 → 总部`。

### 2.2 每一层赚多少

假设链为 `买家 → L0 → L1 → … → Ln → 总部`，本次名额数 `n`：

| 层级       | 收入                     | 成本                 | 利润                                      |
| -------- | ---------------------- | ------------------ | --------------------------------------- |
| L0（直接上级） | 买家实付 `P`               | `costUnit[L0] × n` | `P − costUnit[L0]×n`                    |
| Li（i≥1）  | `costUnit[L(i-1)] × n` | `costUnit[Li] × n` | `(costUnit[L(i-1)] − costUnit[Li]) × n` |
| 总部       | `costUnit[Ln] × n`     | `6500 × n`         | `costUnit[Ln]×n − 6500×n`               |

**为什么 Li 的收入是 `costUnit[L(i-1)]×n`？**  
因为下级 `L(i-1)` 向上级 `Li` 买名额时，付的是**自己档位的拿货单价**（这是固定挂牌价，不随卖方变化）。

### 2.3 买家实付 `P` 的三种来源

| 场景                   | 公式                               | 举例            |
| -------------------- | -------------------------------- | ------------- |
| **新客开卡**（普通用户 → VIP） | 目标档位标价                           | 付 9,980       |
| **升级**（VIP → 天使）     | 目标档位**标价全款**（用户 2026-10-23 最终口径） | 付 29,800      |
| **补名额**（已是某档，再买 n 个） | `costUnit[本档] × n`               | 天使买 1 个：7,500 |

## 三、平级奖（2%，**只发一份给 A，由链顶/总部承担**）

> 用户 2026-10-23 最终口径（修正点）：之前误把「每对同级各发一份」算成 260，正确应为 **仅 A 得一份 130**。

### 3.1 触发条件（关键）

- 买家 B 向**同级上级 A** 补名额（`targetTier === buyerTier`，即**不算升级身份**）→ A 的拿货价 = B 的拿货价 → A 这笔转手利润 **0（不赚钱）**。
- **升级身份不产生平级奖**（升级时下级付更高档位价，卖方必吃差价，必有赚）。
- 收款人 = 链中**第一个与买家同级**的卖方，即不赚钱的那位 **A**，**唯一一份**。

### 3.2 承担方（付款人）

- A 的上级（A 找其买名额的那位）**正常吃差价、不付平级奖**；

> 🟢 **【2026-10-26 覆盖】**：平级奖出资方已改为**从供货上级级差中扣**（与实时下单 `commission.parityPlan` 同口径），取代旧「链顶/总部额外出账」。

- 平级奖由 **A 的供货上级**（链中 A 的上一级）从其**供货级差中扣除** → 预算中性：非额外出账、非总部吸收；
- **基数** = 该供货上级拿货单价 × 2% × 名额数；
- 若 A 已是**链顶**（无供货上级）→ 无资金来源 → **不发**平级奖。

```
平级奖 = 供货上级拿货单价 × 2% × 名额数 ，收款人 = A（链中第一个与买家同级者），出资方 = A 的供货上级（从其级差扣）
```

### 3.3 用户三个算例（全部复现，各 1 份给 A）

| 算例 | 链路                            | 收款人                     | 出资方（从其级差扣）  | 金额（1 名额）              |
| -- | ----------------------------- | ----------------------- | ----------- | --------------------- |
| ①  | B(天使) ← A(天使) ← C(私董) ← D(联创) | **A**（天使）               | C（私董 6,980） | 6980×2%×1 = **139.6** |
| ②  | B(天使) ← A(天使) ← Z(联创)         | **A**（天使）               | Z（联创 6,500） | 6500×2%×1 = **130**   |
| ③  | B(天使) ← A(天使) ← F(联创) ← E(联创) | **仅 A**（F/E 同级**不再发奖**） | F（联创 6,500） | 6500×2%×1 = **130**   |

> ⚠️ 算例③ 修正说明：F 与 E 虽同为联创、F→E 不赚钱，但平级奖**只发给与买家同级的 A**；F/E 的同级不另外发奖。故算例③ 合计 **130**（之前误算 260）。
>
> ⚠️ 算例① 修正说明（2026-10-26）：出资方是 **A 的供货上级 C**（不是链顶 D），故基数取 C 的拿货价 **6,980**（旧口径按链顶 6,500 算成 130）。

### 3.4 与级差的关系（算例③完整分配）

买家 B（天使）补 1 个名额，付 7,500（**不算升级**）：

| 层级    | 收入    | 成本    | 级差利润                  | 平级奖                  |
| ----- | ----- | ----- | --------------------- | -------------------- |
| A（天使） | 7,500 | 7,500 | **0**                 | **130**（收款人 A）       |
| F（联创） | 7,500 | 6,500 | 1,000 − 130 = **870** | 出资方（从 F 级差扣 130）     |
| E（联创） | 6,500 | 6,500 | **0**                 | —（链顶无供货上级→不发）        |
| 总部    | 6,500 | 6,500 | 0                     | —                    |
| 合计    |       |       | **870**               | **130**（级差内部转移，预算中性） |

> 闭环：买家实付 7,500 = 总部成本 6,500 + 级差合计 870 + 平级奖 130 → **平级奖不破坏闭环**。

### 4.0 本金锚点（principal_tier，2026-10-26 新增）

- **字段**：用户表新增 `principal_tier`（本金档）= 用户**实际付过钱的最高档一口价**对应的档位；前台「本金」金额 = `RETAIL_PRICE[principal_tier]`。
- **维护规则**：
  - 入口首购 / 付费升档（`createOrder` 非批发路径）→ `principal_tier = packageTier`（累计已付）。
  - 批发补货（`rawQuota`）→ 不改本金。
  - 免费升档（后台 `updatePartner` 仅改 `tier`；或后续"拉人达标"机制）→ **不动** `principal_tier` —— 这是漏洞防火墙（防止拉人升档后按抬高档少付钱）。
- **计价锚点**：升级自付费价 = `max(0, RETAIL[目标档] − RETAIL[本金档])`，**直接按 RETAIL 相减**（兼容"本金档与目标档不相邻"的跨度），不再以客户端 `oldTier` 当减数。
  - 效果示例：入口 angel（本金 29,800）→ 免费升 private（仅 `tier` 变）→ 再一口价升 cofounder，应付 = 239,800 − 29,800 = **210,000**（而非 239,800 − 59,800 = 180,000）。
- **展示**：`GET /partner/overview` 新增 `principalTier` / `principal`；后台 `GET /api/users` 返回用户裸对象（天然含 `principal_tier`）。
- 回归：`scripts/verify_principal_field.js`（10 项断言）。

### 4.0.1 拉人免费升档触发（2026-10-26 新增）

> 用户口径："拉我三个同级的人升级 → 我免费升 1 档"。

- **规则**：上级 U 直推 **N=3** 名「被推荐时与 U 同级」的下级，且每名下级各自「从同级起步付费升档」，则 U **免费升 1 档**（`tier +1`，`principal_tier` **不变**）。每满 3 名触发一次，可累计（6 名 → 升 2 档），封顶到联创。
- **"同级"判定（推荐快照，不漂移）**：下级被推荐时记录 `referral_upline_tier`（= 当时上级档位）与 `referral_tier`（= 本人当时档位）。下级"合格"当且仅当：`referral_upline_tier` 有值，且存在 `oldTier === referral_upline_tier` 且 `packageTier` 更高的**付费升档订单**（免费授级 / 批发补货不计）。
  - 例：U 为天使时推荐 D，D 付费升 angel→private → D 合格（oldTier=angel=referral 档）。若 D 先 vip→angel（oldTier=vip≠angel）再 angel→private，则仅 angel→private 那笔计入。
- **"免费升档"语义边界**：只改 `tier`，**不动 `principal_tier`**（与 §4.0 防火墙一致）；不触发平级奖/供货级差（非交易，无订单）；不级联触发上级（避免无限递归）；自动重算对外编号；升到联创时置 `daysSinceCofounder`（全球奖无责期）。
- **幂等**：已发放数记 `free_upgrade_applied`，重复调用只补足差额；发放明细写入 `db.freeUpgradeLog`。
- **展示**：`GET /partner/overview` 新增 `referralFreeUpgrade = { required, qualifying, applied, earned, pending, nextTier }`（前端可据此展示"再拉 N 人可免费升档"）。
- **落点**：`src/store.js`（`maybeGrantFreeUpgrade` / `qualifyingDownlineIds` / `referralFreeUpgradeProgress`，常量 `FREE_UPGRADE_REQUIRED=3`、`FREE_UPGRADE_NEXT`）；钩子在 `src/routes.js` 的 `createOrder` 付费升档分支（仅 `rawQuota==null && isUpgrade` 触发）。
- 回归：`scripts/verify_referral_free_upgrade.js`（27 项断言：3 名触发 / 6 名升 2 档 / 不合格不计入 / 本金不动 / 幂等 / 一口价锚定）。

## 五、升级的两种方式

### 方式 A：补差价直升（截图 3）

```
应补金额 = 目标档位标价 − 已缴累计
```

| 场景              | 已缴     | 目标标价    | 应补            |
| --------------- | ------ | ------- | ------------- |
| 截图 3 弹窗：私董 → 联创 | 79,800 | 239,800 | **160,000** ✅ |
| VIP → 私董        | 9,980  | 59,800  | **49,820**    |

- 升级&#x540E;**「初始金额」变为新档位标价**（联创 239,800）。

### 方式 B：推广达标免费升（图 2 第 3 条）

```
达标名额 = 3 × 当前档位名额数
```

| 升级路径     | 需直推名额          | 等价的推荐组合（任选其一）        |
| -------- | -------------- | -------------------- |
| VIP → 天使 | 3 × 1 = **3**  | 3 VIP                |
| 天使 → 私董  | 3 × 3 = **9**  | 9 VIP / 3 天使         |
| 私董 → 联创  | 3 × 6 = **18** | 18 VIP / 6 天使 / 3 私董 |

- 与你说的「私董升联创可以拉 18 个 VIP 或 6 个天使」完全一致 ✅
- 与图 2「1 年内直推三个本级的」一致（3 私董 = 18 名额）✅
- 有效期：开通合伙人之日起 1 年内
- **拉人升级身份变更，但「初始金额」不变**（不产生资金流）

### 5.1 「初始金额」概念

| 升级方式  | 身份      | 初始金额                  |
| ----- | ------- | --------------------- |
| 花钱补差价 | 变更为目标档位 | 变为目标档位标价（如 239,800）   |
| 拉人达标  | 变更为目标档位 | **保持原值不变**（如仍是 9,980） |

作用：后续若再走「补差价升级」，差额按「目标标价 − 初始金额」计算。

## 六、复购奖（2%，用户 2026-10-23 明确口径）

```
复购奖 = 下级本次【实付金额】 × 2%，发给该下级的【直接上级】
```

- **触发**：自己的【下级】购买【任意产品】（任何一笔产品消费，不限是否首次/复购）。
- **收款人**：该下级的**直接上级**（绑定上级），唯一一份。
- **金额**：按下级**实付金额**的 2%，不是按标价、不是按利润。

> 与「名额级差」区分：级差只发生在**名额/批发**流转（§二）；复购奖发生在**产品购买**场景，是上级对下级日常消费的分润，二者互不包含。

示例：`repurchaseBonus({ paid: 7800, downlineId:'B', uplineId:'A' })` → A 得 156。
