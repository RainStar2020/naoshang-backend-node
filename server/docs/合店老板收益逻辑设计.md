# 合店老板收益计算逻辑设计

> 版本：v1.3（2026-10-24 修订：13% 归属改为「被推荐人的上级是否为合店老板」判定）  
> 规则来源：用户 2026-10-23 口述 + 《脑商俱乐部·合店老板》两张截图  
> 实现模块：`src/costorePlan.js`（全部比例、月费、月数、资格、无责月数均可配置，不写死）  
> 验证脚本：`node scripts/verify_costore_plan.js`（**56 条断言，全 PASS**）  
> 覆盖范围：**仅合店老板（合店费）**。合伙人（批发商）见 `合伙人收益逻辑设计.md`。
>
> 二次澄清要点：①分红池**单店独立**（自己分自己的）；②**无责分红**按「合店老板**入股首月**」算（非门店开业月），且 `graceMonths` 做成后台可改；③**业绩不含合店费**（只算本人售出的产品/会员/VIP）；④「推荐人=上级且非合店老板」→上级只拿 2%、13% 归门店老板；⑤业务上**不允许退店**。

## 一、合店费（可配置）

| 项    | 默认值             | 说明                                            |
| ---- | --------------- | --------------------------------------------- |
| 月费   | **698 元/月**（暂定） | `config.monthlyFee`，可按城市标准改                   |
| 起付月数 | **6 个月**        | `config.minMonths = 6`，可自定义 12 个月             |
| 总额   | 月费 × 月数         | 698×6 = 4,188；698×12 = 8,376                  |
| 成为条件 | **VIP 及以上合伙人**  | `config.minTierForOwner = 'vip'`，普通用户不可成为合店老板 |

> ⚠️ 任何少于 6 个月的起付都会抛错（`costoreFeeTotal` 内校验），符合「6 个月起付」硬约束。  
> ⚠️ 业务规则：**入股后不允许退店**（系统不提供退店/退款操作，6 个月起步即锁定）。

## 二、合店费分配总览（合计 100%）

| 归属         | 比例      | 收款对象            |
| ---------- | ------- | --------------- |
| 总部         | 15%     | 平台              |
| 省          | 2%      | 省级代理            |
| 市          | 8%      | 市级代理            |
| 区/县        | 10%     | 区县级代理           |
| **总部体系小计** | **35%** |                 |

## 三、业务 15% 的三场景（核心，2026-10-24 修订）

> **2026-10-24 口径修订**：13% 直推奖的归属以「**被推荐人（新合店老板）的上级是否为合店老板**」判定，**不再以推荐人身份判定**（推荐人概念保留用于记录，但不再决定 13% 流向）。2% 复购奖始终付给**被推荐人的上级**（若存在），否则归门店店长。

设：**上级** `upline` = **被推荐人（新合店老板，即缴纳这笔合店费的人）自己的直接上级**（在合伙人批发体系里进货/拿名额的人）、**门店店长** `storeManager`（拿 40% 服务，同时是 13%/2% 的兜底收款人）。

| 场景    | 条件                                 | 13% 直推奖   | 2% 复购奖 | 门店店长合计              |
| ----- | ---------------------------------- | --------- | ------ | ------------------- |
| **B** | 被推荐人**有上级**，**且上级是合店老板**         | 上级（合店老板）  | 上级（合店老板） | **40%**（业务 15% 全归上级） |
| **C** | 被推荐人**有上级**，**且上级不是合店老板**        | 门店店长      | 上级     | 40% + 13% = **53%** |
| **D** | 被推荐人**无上级**                       | 门店店长      | 门店店长   | 40% + 15% = **55%** |

> 旧模型中的「场景 A（推荐人是合店老板且无上级）」已在 2026-10-24 修订中移除——无上级时统一按场景 D 处理（13% + 2% 全归门店店长）。

### 3.1 统一两槽位模型（永远刚好 15%）

```
13% 直推奖 → 上级（当且仅当上级是合店老板）否则 → 门店店长
 2% 复购奖 → 上级（若存在）否则 → 门店店长
```

- 两槽位都不会落空，业务 15% 永远分完。
- 场景 B：上级既是合店老板，13% + 2% 合并 15% 全归该合店店长（上级=合店老板，业务 15% 全归其本人）。
- 场景 D：13% + 2% 都归门店店长 = 门店店长 15%（叠加 40% 服务 = 55%）。
- 场景 C：上级非合店老板 → 13% 给门店店长、2% 给上级。

> **台账归类（2026-10-26 落地）**：上述 13% 直推与 2% 复购在结算台账中按收款人精准记 `subtype`——上级实拿时记 `costore_upline_direct` / `costore_upline_repurchase`（归「合伙人」身份栏）；无上级兜底给门店店长时记 `costore_store_direct` / `costore_store_repurchase`（归「合店店长」栏）；门店服务 40% 记 `costore_store_service`。报表/对账单可据此按 `subtype` 清晰分离每一笔，上级复购奖不再混在「合店」大桶里。

> **关键澄清（上级是谁）**：2% 复购奖付给**被推荐人（新合店老板）的上级**，与推荐人是否为同一人皆可，但推荐人自己的上级绝对不拿这 2%（模型里没有「推荐人的上级」这个收款入参）。当推荐人恰好等于被推荐人的上级、且此人不是合店老板时，他只拿 2%，13% 直推奖因上级非合店老板而归门店店长——即「上级只拿 2%，剩下 13% 归门店店长」；若此人本身是合店老板，则同人拿 13%+2%=15%（场景 B）。

### 3.2 以 1 个月（698 元）为例的实算

| 场景 | 上级是合店老板（B） | 上级非合店老板（C） | 门店店长        | 分红池   | 合计  |
| -- | ----------- | ----------- | ----------- | ----- | --- |
| B  | 104.70（13%+2%） | —           | 279.20（40%） | 69.80 | 698 |
| C  | —           | 13.96（2%）    | 369.94（53%） | 69.80 | 698 |
| D  | —           | —           | 383.90（55%） | 69.80 | 698 |

（总部 104.70 + 省 13.96 + 市 55.84 + 区县 69.80 另计，三场景相同。）

### 3.3 与昨天实现的关系

昨天实现的固定三分结构「门店老板 53% + 推荐人 2% + 分红 10%」**正好等价于本规则【场景 C】**。  
本设计在其基础上把 53% 拆成「服务 40% + 直推 13%」，使 13% 可流向被推荐人的上级（当其是合店老板时，即场景 B，业务 15% 全归上级），并在无上级时归门店店长（场景 D，55%）。**2026-10-24 起，13% 的归属判定由「推荐人是否合店老板」改为「被推荐人的上级是否合店老板」。**

## 四、分红（单店独立，两池同一分配规则）

### 4.1 两个分红池（均按**单店**独立计算，自己分自己的）

| 池子             | 金额来源                                                                              | 默认                  |
| -------------- | --------------------------------------------------------------------------------- | ------------------- |
| 合店费分红          | 本店合店费 × **10%**（= 698 × 月数 × 本店合店老板人数 × 10%）                                      | 单店 3 人×1 月 = 209.40 |
| 软件卡 / VIP 会员分红 | **100 元/月/单位**（`config.softwareUnitPrice`，可改）× 计入比例（`softwareToPoolRate`，默认 100%） | 10 单位 = 1,000       |

> 两池都**单店独立**：A 店的池只分给 A 店的合店老板，B 店同理，互不串（验证 §5b 已覆盖）。

### 4.2 分配规则（两池共用）

```
一半：按「本店合店老板人数」均分
另一半：按「各自业绩比例」分
```

- **业绩口径**：只算该合店老板**本人卖出的**产品 / 会员 / VIP 合伙人金额，**不含其缴纳的合店费**（验证 §5c 已覆盖）。

### 4.3 分红资格（按月，无责分红按「入股首月」）

- 当月至少直推 **1 个** 合店老板 / 季卡会员 / VIP 合伙人（或售出产品），才有资格参与当月分红。
- **无责分红 = 合店老板「入股」的首 `graceMonths` 月**（免考核直接有资格）。注意：是**每个合店老板自己入股的那个月**起算，**不是门店开业的第一个月**（验证 §5 / §7 已覆盖）。
- **无责分红月数 `graceMonths` 由总部后台可调**（默认 1 个月），例如总部可改成 3 个月（验证 §7 已覆盖）。
- 不合格者当月分红 = 0，其份额由合格者按同一规则分摊（池子总额固定）。

## 五、接口清单（`src/costorePlan.js`）

| 函数                                                                  | 用途                                |
| ------------------------------------------------------------------- | --------------------------------- |
| `DEFAULT_CONFIG`                                                    | 全部默认比例/月费/月数/资格/无责月数（可整体覆盖）       |
| `rateSum(config)` / `assertRates(config)`                           | 比例合计校验（必须 100%）                   |
| `canBeCostoreOwner(tier, config)`                                   | 是否 VIP 及以上（准入门槛）                  |
| `costoreFeeTotal({monthlyFee, months, config})`                     | 合店费总额（校验 ≥6 个月）                   |
| `costoreDistribution({...})`                                        | **核心**：一笔合店费按三场景整笔分配（含 100% 闭环校验） |
| `describeScenario({uplineIsCostoreOwner, hasUpline})`               | 返回 B/C/D 场景码与说明（2026-10-24：以被推荐人上级是否合店老板判定） |
| `qualifyForDividend({joinedMonthsAgo, salesMet, graceMonths})`      | 分红资格（入股首月无责，之后需达标）                |
| `dividendSplit({pool, owners, config})`                             | **单店**分红池一半人数、一半业绩分配（含资格过滤）       |
| `storeDividendPool({ownerCount, feeMonths, softwareUnits, config})` | 单店池聚合（合店费10% + 软件卡/VIP）           |
| `softwareDividendPool({units, perUnit, config})`                    | 软件卡/VIP 分红池金额                     |
| `costorePlanTable(config)`                                          | 比例速查表                             |

### 调用示例

```js
const C = require('./src/costorePlan');

// 场景 B：被推荐人 L 的上级 U 是合店老板，门店店长 M，交 6 个月
//   （2026-10-24：13% 以「被推荐人的上级是否为合店老板」判定，不再看推荐人）
const res = C.costoreDistribution({
  months: 6,
  storeManagerId: 'M',
  upline: { id: 'U' },                 // 被推荐人的上级（在其合伙人体系直接绑定）
  uplineIsCostoreOwner: true,           // 上级 U 是合店老板 → 场景 B，业务 15% 全归 U
  referrer: { id: 'R', isCostoreOwner: true }, // 推荐人仅记录，不再决定 13% 流向
});
console.log(res.scenario);      // { code:'B', label:'上级是合店老板 → 上级拿 13%直推 + 2%复购 = 15%' }
console.log(res.byRecipient);   // M 1675.20 / U 104.70 / HQ 628.20 ...（U 拿 13%+2%）
console.log(res.closure);       // true（100% 闭环）

// 单店分红：按「入股首月无责 / 之后需达标」过滤后，一半人数、一半业绩
C.dividendSplit({
  pool: 1000,
  owners: [
    { id:'o1', performance:100, joinedMonthsAgo:3, salesMet:true },
    { id:'o2', performance:300, joinedMonthsAgo:3, salesMet:true },
    { id:'o3', performance:500, joinedMonthsAgo:3, salesMet:false },        // 不合格
    { id:'o4', performance:100, joinedMonthsAgo:0, salesMet:false },        // 入股首月无责
  ],
});

// 单店池聚合：合店费 10% + 软件卡/VIP
C.storeDividendPool({ ownerCount: 3, feeMonths: 1, softwareUnits: 10 });
```

### 关于 #1「上级」的口径（已确认）

经你澄清：**2% 复购奖付给「被推荐人（新合店老板）自己的上级」，推荐人的上级不拿钱**。

我在两槽位模型里已把 `upline` 建模为**缴纳这笔合店费的合店老板（被推荐人）在合伙人批发体系里的直接绑定上级**（他进货/拿名额的那个上级），与「推荐人」是两个独立入参，可同可异：

- 2% 复购奖 → 给这个「被推荐人的上级」。
- 模型里**没有「推荐人的上级」这个收款方**，因此推荐人的上级天然不拿钱（与你说的完全一致）。
- 当推荐人恰好等于这个上级、且他不是合店老板/门店老板时，他就只拿 2%，13% 归门店老板。
- 这样可平滑衔接已有的合伙人绑定链（`partnerGrade` 的 upline 关系）。

## 七、与现有代发（结算链路）的衔接 —— 推荐方案

**背景**：现有 `src/commission.js` 的 `COSTORE_RATE`（门店老板 53% / 推荐人 2% / 分红 10%）正好对应本规则的【场景 C】；结算链路（`settlement.js` / `routes.js` / H5）仍在用旧结构。本模块已按 A/B/C/D 四场景补全。

**推荐方案：方案二 —— 配置开关切换 + 旧逻辑保留回滚（Adapter with flag）**

| 维度    | 说明                                                                                                                                                                                        |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 思路    | 在 `settlement.js` 的 `runCostore` 里加开关 `config.costorePlanV2`（默认 **true**，因新规则是场景 C 的严格超集、数值一致、切换低风险）；`true` 走 `costorePlan.costoreDistribution`，`false` 走旧 `coStoreFeeAllocation`（保留做回滚）。 |
| 数据派生  | ① 推荐人 = 现有 `promoter_id`；是否合店老板 = 查合店老板表。② 上级 = 该合店老板在合伙人表的绑定上级（`partnerGrade` upline）。③ 单店分红需新增「合店老板入股记录」(`joinDate`/`storeId`)。                                                         |
| 幂等    | 复用现有 `upsertCommission`（按 id 覆盖），连跑不翻倍。                                                                                                                                                   |
| 后台可调项 | 月费、起付月数、**无责分红月数 graceMonths**、软件卡单价/计入比例 全部走 `DEFAULT_CONFIG` 并由后台设置页覆盖。                                                                                                                 |
| 风险    | 旧逻辑 100% 保留，开关一关即回退；且先在小范围门店灰度。                                                                                                                                                           |

> 不推荐的方案：①「整体替换旧函数」—— 风险集中、无回滚；②「新旧并存两条结算」—— 数据双写易乱、对账困难。故推荐方案二。
